# 灵犀 - 完整使用指南

> 版本: v2.0.3 | 平台: Telegram / QQ (aiocqhttp)

---

## 一、插件概述

灵犀（astrbot_plugin_smart_wakeup）是一套"群友型 Bot 节律引擎"——它不仅能在群聊消息包含机器人名称、关键词时自然回复，还内置基于 AIF（Anticipation-Initiation-Planning，预期-发起-规划）模型的主动发言引擎：周期性感知群内氛围，在合适时机主动发起话题、分享 RSS 实时资讯；同时具备五路退却机制与静默时段，被无视时知趣收声、到点按时睡觉。配合精力系统与心流状态机，模拟真人的社交节奏与精力变化。

### 核心特性

| # | 特性 | 说明 |
|---|------|------|
| 1 | 名称触发 | 消息包含机器人名称/别名即触发，确定性回复 |
| 2 | 关键词触发 | 消息包含关注关键词时按概率回复 |
| 3 | 多别名 | 支持 `\|` 分隔多个别名，大小写不敏感 |
| 4 | 概率唤醒 | 未命中名称/关键词时也有概率主动回复，概率由精力、心流等因子动态计算 |
| 5 | 主动发言引擎 | 基于 AIF（Anticipation-Initiation-Planning）模型周期性主动发起话题，与被动回复共享记忆体系 |
| 6 | 资讯注入（Fetcher） | RSS（内置 15 个中文源、4 大类）+ 资讯 API 双通道，跨群去重，为主动发言提供实时素材 |
| 7 | 五路退却机制 | 活跃激增 / 连续 SKIP / 厌烦关键词 / 自说自话 / 连续无回应，任一路触发即知趣收声 |
| 8 | 静默时段 | 支持多个跨午夜时段（如 `23:00-07:00,13:00-14:00`），可单群覆盖 |
| 9 | 精力系统 | 模拟社交疲劳，防止过度活跃 |
| 10 | 心流状态机 | 四状态（旁观→关注→心流→疲劳）动态调整回复策略 |
| 11 | 冷场救场 | 检测群聊停滞时主动参与对话 |
| 12 | 消息防抖 | 等待用户停止发言后再判定回复，避免打断补充发言 |
| 13 | 复读抑制 | 检测复读链时大幅降低概率唤醒概率，避免打断群友复读氛围 |
| 14 | 回复抑制 | [SKIP] 关键词前缀拦截（零成本，防止思考泄露）+ 独立小模型合规判别，双重抑制 |
| 15 | 轻量回应 | 回复被抑制时偶尔掉落"确实""有道理"等短语，概率+冷却+每小时上限三重防护 |
| 16 | 分层对话记忆 | 保留最近 N 轮原文，更早对话压缩为摘要，支持连贯多轮对话 |
| 17 | 上下文压缩 | 将群聊上下文压缩后再注入主模型，大幅减少 token 消耗 |
| 18 | 模型路由 | 简单消息由小模型回复，复杂消息由大模型回复 |
| 19 | 消息分段 | 将长回复智能分段发送，模拟真人输入节奏 |
| 20 | 图片上下文关联 | 让 Bot 理解图片内容，避免图片+文本消息的上下文断裂 |
| 21 | 在场用户感知 | 标注近期活跃用户，防止 Bot 对不在场的用户说话 |
| 22 | 对话关系标注 | 标注 BOT 发言、回复关系、隐式回应，帮助 LLM 理解对话流 |
| 23 | 可视化配置面板 | 专属 Web 面板：分组标签页、5 秒实时状态轮询、预设切换、测试发言、日志控制台 |
| 24 | 主动发言状态持久化 | 退却状态/冷却/每日计数持久化至 proactive_state.json，插件重载不丢失 |

### 支持平台

| 平台 | 适配器 | 群 ID 格式 |
|------|--------|-----------|
| Telegram | 内置适配器 | 负数（如 `-1001234567890`） |
| QQ | aiocqhttp | 正数（如 `123456789`） |

## 二、部署步骤

### 2.1 安装

**方式一：插件市场（推荐）**

在 AstrBot WebUI → 插件市场 中搜索「灵犀」或「smart_wakeup」，一键安装。

**方式二：手动安装**

将 `astrbot_plugin_smart_wakeup` 文件夹放入 AstrBot 的 `data/plugins/` 目录，然后在 WebUI 插件管理页面启用。

### 2.2 前置条件

| 条件 | 说明 |
|------|------|
| AstrBot >= v4.16（< v5） | 核心框架版本要求 |
| LLM 提供商 | 至少配置一个 LLM 服务商（如 OpenAI、Volcengine 等） |
| 人格设定 | 推荐在 AstrBot 中配置人格，回复质量更佳 |
| 平台适配器 | 已配置 Telegram 或 QQ (aiocqhttp) 适配器 |

### 2.3 验证安装

在群聊中发送包含机器人名称的消息，观察：

- AstrBot 日志中出现 `名称自然唤醒: 命中名称 'xxx'` 或 `灵犀` 相关日志
- 机器人自动回复

### 3.6 主动发言

主动发言引擎是 v2.0 的核心：Bot 不再只等待被 @，而是周期性感知群内氛围，在合适时机主动发起话题。详细机制见 [4.15 主动发言引擎](#415-主动发言引擎)。

| 配置项 | 类型 | 默认值 | 说明 |
|--------|------|--------|------|
| `proactive_enabled` | bool | `false` | 启用主动发言，默认关闭 |
| `proactive_check_interval` | int | `600` | 检查间隔（秒），每隔多久评估一次是否发言 |
| `proactive_model` | string | `""` | 主动发言模型提供商 ID，留空使用当前 LLM 提供者 |
| `proactive_cooldown` | int | `1800` | 两次主动发言之间的冷却时间（秒） |
| `proactive_daily_limit` | int | `20` | 每群每日主动发言上限 |
| `proactive_probability` | float | `0.6` | 每次检查通过后的触发概率（0~1） |
| `proactive_min_energy` | float | `0.15` | 精力下限，精力低于此值时不主动发言 |
| `proactive_time_window_start` | string | `09:00` | 允许主动发言的起始时间 |
| `proactive_time_window_end` | string | `23:00` | 允许主动发言的结束时间 |
| `proactive_quiet_hours` | string | `23:00-07:00` | 静默时段，支持多个跨午夜时段（如 `23:00-07:00,13:00-14:00`），可单群覆盖 |
| `proactive_min_context_messages` | int | `1` | 最少上下文消息数，群内消息少于此数时不主动发言 |
| `proactive_idle_threshold` | int | `600` | 冷场判定阈值（秒），群聊沉默超过此值才考虑主动发言 |
| `proactive_self_talk_ratio` | float | `0.8` | 自说自话占比阈值，超过则触发退却 |
| `proactive_self_talk_hours` | float | `2.0` | 自说自话检测时间窗口（小时） |
| `proactive_topic_categories` | string | `分享想法\|提问讨论\|回忆过去\|关注某人\|活跃气氛\|科技资讯\|游戏八卦\|沙雕新闻\|热点事件` | 话题类别，9 类内置话题，用 `\|` 分隔 |
| `proactive_custom_topics` | string | `""` | 自定义话题，用 `\|` 分隔，加入话题池参与随机选取 |
| `proactive_target_groups` | string | `""` | 主动发言目标群列表，留空则所有群生效 |
| `proactive_retreat_active_surge_secs` | int | `3600` | 活跃激增退却时长（秒），群内突然热闹时主动让位 |
| `proactive_retreat_consecutive_skip_secs` | int | `3600` | 连续 SKIP 退却时长（秒），主动发言连续被抑制后收声 |
| `proactive_retreat_no_response_base_secs` | int | `3600` | 连续无回应退却基础时长（秒） |
| `proactive_retreat_no_response_max_secs` | int | `86400` | 连续无回应退却最大时长（秒），按 2h/6h/24h 阶梯递增 |
| `proactive_retreat_annoyed_secs` | int | `86400` | 厌烦关键词退却时长（秒），检测到"闭嘴""烦"等信号后长时间收声 |

### 3.10 回复抑制

双重回复抑制机制，让 Bot 在该沉默时保持沉默，且绝不泄露思考内容。详细机制见 [4.16 回复抑制与轻量回应](#416-回复抑制与轻量回应)。

| 配置项 | 类型 | 默认值 | 说明 |
|--------|------|--------|------|
| `reply_suppression_enabled` | bool | `false` | 启用回复抑制，默认关闭 |
| `reply_suppression_mode` | string | `keyword` | 抑制模式：`keyword`（关键词前缀拦截）/ `judge`（小模型合规判别） |
| `reply_suppression_keyword` | string | `[SKIP]` | 抑制关键词，LLM 回复以此开头时拦截整条回复 |
| `reply_suppression_judge_model` | string | `""` | 判别模型提供商 ID，judge 模式下使用，留空使用当前 LLM 提供者 |
| `reply_suppression_judge_prompt` | string | `""` | 自定义判别提示词，留空使用内置提示词 |

### 3.11 轻量回应

回复被抑制时，偶尔掉落一两个字证明"在场但不想多说"。概率 + 冷却 + 每小时上限三重防护，避免刷屏。

| 配置项 | 类型 | 默认值 | 说明 |
|--------|------|--------|------|
| `light_response_enabled` | bool | `true` | 启用轻量回应 |
| `light_response_prob` | float | `0.3` | 触发概率（0~1），仅在回复被抑制时参与判定 |
| `light_response_cooldown` | int | `300` | 冷却时间（秒） |
| `light_response_max_per_hour` | int | `3` | 每小时上限 |
| `light_response_pool` | string | `确实\|是这样的\|嗯\|有道理\|哈哈\|学到了\|原来如此\|有点意思` | 自定义话语库，用 `\|` 分隔 |

### 3.13 高级设置

#### 单群参数覆盖（group_overrides）

为特定群组覆盖全局参数，只需填写需要覆盖的字段。共支持 21 个覆盖字段：

- **精力**：`energy_decay_rate`、`energy_recovery_rate`
- **心流**：`flow_bystander_prob`、`flow_attentive_prob`、`flow_flow_prob`、`engagement_decay_per_minute`、`engagement_refresh_on_reply`、`fatigue_coefficient`、`fatigue_max_multiplier`
- **冷场救场**：`rescue_idle_threshold`、`rescue_cooldown`
- **消息防抖**：`debounce_wait_name`、`debounce_wait_prob`、`debounce_wait_rescue`
- **关键词**：`keyword_reply_prob`
- **主动发言**：`proactive_enabled`、`proactive_cooldown`、`proactive_daily_limit`、`proactive_probability`、`proactive_min_energy`、`proactive_quiet_hours`

每个覆盖项需填写 `group_id`（群组 ID）和需要覆盖的字段，未填写的字段使用全局默认值。通过单群覆盖，海外时区的群可以单独配置静默时段，同一个 Bot 在每个群都可以有不同的人设。

#### 用户回复概率覆盖（user_prob_overrides）

为特定用户自定义回复概率乘数。每个覆盖项需填写 `user_id`（用户 ID）和 `reply_prob`（0~1 之间，0=永不回复，1=正常概率，0.5=概率减半）。

#### 分段高级参数（splitter_advanced）

| 配置项 | 类型 | 默认值 | 说明 |
|--------|------|--------|------|
| `max_segments` | int | `7` | 均分模式下的最大分段数 |
| `min_segment_length` | int | `10` | 均分模式下避免切出过短碎片 |
| `linear_base` | float | `0.5` | 线性基础值（秒） |
| `linear_factor` | float | `0.1` | 线性字数系数，延迟 = 基础值 + 字数 × 系数 |
| `log_base` | float | `0.5` | 对数基础值（秒） |
| `log_factor` | float | `0.8` | 对数系数，延迟 = 基础值 + 系数 × ln(字数+1) |
| `random_min` | float | `1.0` | 随机最小值（秒） |
| `random_max` | float | `3.0` | 随机最大值（秒） |
| `fixed_delay` | float | `1.5` | 固定延迟值（秒） |

### 3.14 资讯模块（Fetcher）

为主动发言提供实时资讯素材：RSS 订阅 + 资讯 API 双通道，内置 15 个中文资讯源（科技/游戏/沙雕/热点 4 大类），跨群去重。

| `fetcher_api_key_env` | string | `""` | API Key 环境变量名（可选，优先于直接填写 Key） |
| `fetcher_cache_ttl` | int | `21600` | 缓存 TTL（秒），默认 6 小时 |

## 四、核心系统详解

### 4.1 精力系统

精力系统模拟人类社交疲劳，防止机器人过度活跃。

**消耗规则：**
- 每次回复消耗精力，消耗量 = `energy_decay_rate`
- 精力最低降至 0.0

**恢复规则：**
- 每分钟自然恢复，恢复量 = `energy_recovery_rate`
- 精力最高恢复至 1.0

**与概率唤醒的联动：**
- 精力影响 `energy_factor`：`energy_factor = current_energy`
- 精力为 0 时，概率唤醒完全关闭
- 命中名称/关键词时仍可回复，不受精力限制
- 精力恢复后自动恢复概率唤醒功能

### 4.2 心流状态机

心流状态机根据群聊活跃程度动态调整回复策略，共四种状态：

| 状态 | 说明 | 基础概率 | flow_factor |
|------|------|---------|-------------|
| **旁观** (bystander) | 群聊冷清，安静旁观 | `flow_bystander_prob` (0.08) | 0.2 |
| **关注** (attentive) | 出现相关话题，开始关注 | `flow_attentive_prob` (0.20) | 0.8 |
| **心流** (flow) | 深入对话中，积极参与 | `flow_flow_prob` (0.40) | 1.5 |
| **疲劳** (fatigued) | 精力耗尽，减少回复 | 等同旁观概率 | 0.2 |

**状态转换条件：**

```
旁观 → 关注: 近期有名称命中或话题相关
关注 → 心流: 连续多轮互动，消息密度高
心流 → 疲劳: 精力低于阈值
疲劳 → 旁观: 精力恢复到一定水平
关注 → 旁观: 长时间无互动（参与度衰减至 0）
心流 → 关注: 互动减少
```

**因子映射：** 心流状态通过 `flow_factor` 参与概率唤醒公式计算，旁观和疲劳为 0.2，关注为 0.8，心流为 1.5。

**参与度机制：**
- 参与度随时间衰减，速率由 `engagement_decay_per_minute` 控制
- 概率唤醒或冷场救场回复后，参与度增加 `engagement_refresh_on_reply`
- 参与度影响心流状态的升降

### 4.3 概率唤醒

当消息未命中机器人名称或关键词时，插件根据动态概率决定是否主动回复：

```
P = base_prob × energy_factor × flow_factor × timing_factor
```

| 因子 | 说明 | 取值范围 |
|------|------|---------|
| `base_prob` | 基础概率，由当前心流状态决定 | 0.08 ~ 0.40 |
| `energy_factor` | 精力因子，等于当前精力值 | 0.0 ~ 1.0 |
| `flow_factor` | 心流因子，越深入对话状态概率越高 | 0.2 ~ 1.5 |
| `timing_factor` | 时机因子，考虑消息间隔等时间因素 | 0.5 ~ 1.2 |

此外，复读消息的概率还会乘以 `repeat_suppress_factor`（默认 0.1），大幅降低复读链中的回复概率，避免打断群友的复读氛围。

### 4.4 冷场救场

当检测到群聊长时间无消息后出现新消息时，机器人主动参与对话，打破沉默。

**触发条件：**
- 群聊无消息时间超过 `rescue_idle_threshold`（默认 300 秒）
- 距上次冷场救场超过 `rescue_cooldown`（默认 1800 秒）
- `rescue_enabled` 为 `true`
- 当前精力 > 0

**冷却机制：** 两次冷场救场之间有最短间隔（`rescue_cooldown`），避免频繁救场。

### 4.5 消息防抖

防抖机制等待用户停止发送消息后再判定是否回复，避免打断用户补充发言。

**工作流程：**

```
消息到达 → 判定触发类型
  │
  ├─ 名称触发 / 回复Bot消息 + force_debounce=关闭 → 跳过防抖，立即判定
  │
  └─ 其他情况 → 进入防抖等待
       │
       │  等待期间收到新消息？
       │     ├─ 是 → 重置定时器，继续等待
       │     └─ 否 → 定时器到期
       │
       ▼ 聚合等待期间所有消息，执行回复
```

**自适应等待时间：**

| 触发类型 | 配置项 | 默认值 | 说明 |
|---------|--------|--------|------|
| 名称触发 | `debounce_wait_name` | 5 秒 | 用户明确呼叫，等待较短 |
| 概率唤醒 | `debounce_wait_prob` | 10 秒 | 主动插话，等待较长 |
| 冷场救场 | `debounce_wait_rescue` | 3 秒 | 群聊已停滞，快速救场 |

**消息聚合：** 防抖等待期间收到的所有消息会在定时器到期后一并注入 LLM 上下文，实现完整理解用户意图、避免重复回复。

**强制防抖：** `force_debounce` 为 `true`（默认）时，所有触发类型统一走防抖流程；关闭后名称匹配和回复 Bot 消息可跳过防抖立即判定。

### 4.6 复读抑制

检测群聊中的复读消息并大幅降低概率唤醒概率，避免 Bot 在群友复读时频繁触发回复、打断复读氛围。

**检测模式：**
1. **全文复读：** 归一化后文本完全相同（去除首尾空白、标点、全半角差异）
2. **部分复读：** 当前消息整体是某条历史消息的子串，且长度占历史消息 30% 以上，且长度不小于 `repeat_min_length`

**抑制方式：** 复读消息的概率唤醒概率乘以 `repeat_suppress_factor`（默认 0.1，即降至正常的 10%）。复读消息仍会作为上下文记录到缓冲区。

### 4.7 对话记忆

分层对话记忆使 Bot 能进行连贯的多轮对话，替代被清空的核心上下文。

**分层结构：**

| 层级 | 内容 | 说明 |
|------|------|------|
| 近期原文 | 最近 `recent_rounds_keep` 轮对话的原文 | 每轮包含用户消息和 Bot 回复 |
| 历史摘要 | 更早对话压缩后的摘要 | 由小模型生成，长度不超过原文 20% |

**摘要压缩流程：**
1. 当对话历史超过 `recent_rounds_keep × 2` 条记录时触发
2. 将较旧的记录发送给摘要模型（`summary_model` 或 `compression_model`）
3. 生成的摘要合并到已有摘要中
4. 已摘要的记录从历史中移除

**配置：**
- `recent_rounds_keep`：保留最近 N 轮原文（默认 10）
- `summary_rounds_max`：摘要覆盖的最大轮数（默认 30），超过则丢弃最旧对话，设为 0 则只保留近期原文不生成摘要
- `summary_model`：摘要模型提供商 ID，留空则使用 `compression_model`

### 4.8 上下文压缩

将群聊上下文压缩后再注入主模型，大幅减少 token 消耗。

**增量注入：** 启用后仅注入上次回复后的新消息（`incremental_context_enabled`），新增消息少于 `incremental_context_min_new` 时补充旧消息，确保上下文充足。

**压缩流程：** 当原始上下文字符数超过 200 时，使用独立的小模型（`compression_model`）对上下文进行压缩，压缩后注入主模型。

**绕过核心上下文：** `bypass_core_context`（推荐开启）使唤醒触发的消息清空核心对话历史，仅使用插件自管理的上下文（消息缓冲区 + 增量注入 + 摘要压缩），这是控制 token 消耗的关键方案。仅影响唤醒消息，正常 @ 对话仍使用核心上下文。

### 4.9 模型路由

根据消息复杂度选择不同模型生成回复，降低成本。

**路由逻辑：**
- 简单消息（如打招呼、简单问答）→ 小模型（`routing_small_model`）
- 复杂消息 → 当前 LLM 提供者（大模型）

**级联升级：** `cascade_upgrade_enabled` 当前版本**未实现**——原级联升级逻辑已在后续修复中移除（功能未完成且统计虚高），保留此配置项仅为兼容已有配置结构，开启后无任何效果。请勿依赖此功能。

**配置：**
- `model_routing_enabled`：默认关闭，开启后简单消息由小模型回复
- `routing_small_model`：小模型提供商 ID（如 `Volcengine/doubao-seed-2-0-lite-260215`）

### 4.10 消息分段

将长回复智能分段发送，模拟真人输入节奏。

**智能分段：** 启用 `enable_smart_split` 后，避免在以下位置切断：
- 引号内部（`"..."`、`'...'`、`` `...` ``）
- 成对符号内部（括号等）
- 代码块内部（` ```...``` `）
- think 标签内部（`<think>...</think>`）
- 英文缩写/小数/域名处（U.S.、3.5、.com 不切分）
- 省略号处（`...`、`……` 作为整体保留）

**均分模式：** 启用 `balanced_split_mode` 后，按总字数和段数尽量均匀分配每段长度，避免碎片化。受 `max_segments` 和 `min_segment_length` 约束。

**末尾标点剔除：** 启用 `strip_trailing_punct_enabled` 后，自动剔除每段末尾的指定标点（如 `。；;：:、`），使回复更符合自然聊天习惯。问号和感叹号有语气功能，默认保留。

**延迟策略：**

| 策略 | 计算方式 |
|------|---------|
| `linear` | 延迟 = `linear_base` + 字数 × `linear_factor` |
| `log` | 延迟 = `log_base` + `log_factor` × ln(字数+1) |
| `random` | 延迟 = [`random_min`, `random_max`] 随机值 |
| `fixed` | 延迟 = `fixed_delay` |

### 4.11 思考标签过滤

作为兜底机制，过滤 LLM 回复中思考标签包裹的思考内容，防止泄露给用户。

**两层拦截：**

```
LLM 生成回复
  │
  ▼ 第一层：AstrBot 核心管道过滤
  │     AstrBot 自身可能已处理部分思考标签
  │
  ▼ 第二层：插件兜底过滤（filter_thinking_tags）
  │     正则匹配并移除：
  │     - <think>...</think>
  │     - <think()>...</think()>
  │     - 仅闭合标签 </think>（前面内容为草稿）
  │
  ▼ 发送到群聊
```

**支持的标签格式：**
- `<think>...</think>` — GLM 等模型格式
- `<think()>...</think()>` — AstrBot 格式
- 仅 `</think>` — 模型在 content 中先输出草稿再用 `</think>` 分隔最终版

默认开启（`filter_thinking_tags = true`），推荐保持开启以防止思考内容泄露。

### 4.12 图片上下文关联

让 Bot 理解图片内容，避免图片+文本消息的上下文断裂。默认关闭，需手动开启。

**为什么需要此功能？**

群聊中用户经常发送图片，但 Bot 默认无法理解图片内容。当用户发送图片后追加文字说明时，Bot 缺乏图片上下文，回复可能偏离实际语境。图片上下文关联通过识别图片内容并注入上下文，使 Bot 能准确理解图片+文字的混合消息。

**两种识别来源：**

| 来源 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| **框架图片描述** | AstrBot 框架自动生成图片描述并注入上下文（由 `group_chat_context` 等插件提供） | 零额外 API 成本，无需配置 | 依赖框架异步生成，描述可能延迟到达；依赖其他插件提供描述 |
| **自定义模型识别（降级方案）** | 框架未提供图片描述时，使用自选多模态模型识别图片内容 | 描述更贴合群聊场景，可控性强 | 每张图片额外消耗一次 API 调用 |

**配置指南：**

1. **框架图片描述**：无需开启任何开关，确保 AstrBot 已配置 `group_chat_context` 插件。Bot 会从框架上下文中提取 `[Image: 描述]` 格式的图片描述，更新到消息缓冲区。

2. **自定义模型识别（降级方案）**：开启 `image_context_custom_model`，并在 `image_context_custom_model_id` 中填写支持图片输入的多模态模型提供商 ID（如 `Volcengine/doubao-vision-pro-32k`）。仅当框架未提供图片描述时，Bot 才会异步调用该模型识别图片，生成简洁的中文描述。通常无需开启，仅在框架图片描述功能异常时作为降级方案。

**工作流程：**

```
用户发送图片
  │
  ▼ 缓冲区记录 [图片] 占位符
  │
  ├─ 框架来源：等待框架上下文携带 [Image: 描述] → 更新为 [图片: 描述]
  │
  └─ 降级方案：框架无描述时，异步调用多模态模型 → 更新为 [图片: 描述]
  │
  ▼ 上下文注入时，已识别的图片显示为 [图片: 描述]，未识别的显示为 [图片]
```

> 两种来源为主备降级关系：优先使用框架图片描述，框架未提供时才走自定义模型。此功能默认关闭。

### 4.13 在场用户感知

始终启用，防止 Bot 对不在场的用户说话。

**为什么需要此功能？**

群聊中 Bot 可能因上下文中的历史消息而"幻觉"提及已经离开或长时间未发言的用户，导致对话不自然。在场用户感知通过标注近期活跃用户，约束 Bot 只对在场用户发起对话。

**工作原理：**

1. 插件统计消息缓冲区中近期活跃的用户列表（排除 BOT 自身）
2. 在上下文开头添加 `[近期活跃]` 标注，列出近期发言的用户名
3. 在系统提示中注入 `<presence_awareness>` 指令，要求 Bot 只对近期活跃用户说话

**上下文示例：**

```
[近期活跃]: 用户A, 用户B, 用户C
[用户A]: 今天天气真好
[BOT]: 是啊，适合出去走走
[用户B] (回应BOT): 你也觉得啊
```

> 在场感知是提示词层面的约束，需要配合人格提示词共同生效。如果人格提示词中有冲突指令，可能影响效果。

### 4.14 上下文对话关系标注

始终启用，帮助 LLM 理解对话流和回复关系。

**为什么需要此功能？**

群聊消息交错复杂，LLM 难以仅凭文本判断谁在回复谁、哪条是 BOT 的发言。对话关系标注通过在上下文中添加结构化标记，让 LLM 准确理解对话流向。

**标注格式：**

| 标注 | 含义 | 示例 |
|------|------|------|
| `[BOT]` | BOT 的发言 | `[BOT]: 今天天气真好` |
| `→ 回复[BOT]` | 明确回复 BOT 的消息 | `[用户A] → 回复[BOT]: 你也觉得啊` |
| `(回应BOT)` | 紧跟 BOT 消息 5 秒内的隐式回应 | `[用户A] (回应BOT): 哈哈确实` |

**省略主语提示：**

群聊中用户常省略主语（如"怎么突然就变成XX了？"通常意为"我怎么突然就变成XX了？"）。插件在系统提示中注入 `<conversation_guidance>` 指令，引导 LLM 结合对话关系标注正确理解省略主语的句子。

**上下文示例：**

```
[近期活跃]: 用户A, 用户B
[用户A]: 今天好热
[BOT]: 是啊，都快中暑了
[用户B] (回应BOT): 怎么突然就变成中暑了
[用户A] → 回复[BOT]: 哈哈你也太夸张了
```

### 4.15 主动发言引擎

主动发言引擎是 v2.0 的核心能力，基于 AIF（Anticipation-Initiation-Planning，预期-发起-规划）模型：Bot 周期性评估"现在适不适合说话"，适合时才发起话题，而不是按固定频率刷屏。

**工作状态机：**

| 状态 | 说明 |
|------|------|
| **PASSIVE_MONITORING** | 被动监听：群内氛围正常，Bot 安静观察，不主动发言 |
| **AGENT_DOMINANT** | 主导模式：检测到冷场且条件满足，Bot 主动发起话题带动气氛 |

**发言判定流程：**

```
定时检查（proactive_check_interval，默认 600 秒）
  │
  ▼ ① 群过滤：目标群列表 / 白名单 / 黑名单
  │
  ▼ ② 退却检查：任一路退却生效中 → 跳过（见 4.16）
  │
  ▼ ③ 静默时段检查：处于 quiet_hours 或发言时间窗外 → 跳过
  │
  ▼ ④ 条件检查：冷却期满？未达每日上限？精力 ≥ 下限？
  │     上下文消息数 ≥ 下限？群聊沉默超过 idle_threshold？
  │
  ▼ ⑤ 氛围感知：沉默 / 活跃 / 自说自话 三态判定
  │     ├─ 群内正热闹（活跃激增）→ 触发退却，不插话
  │     └─ 冷场中 → 继续
  │
  ▼ ⑥ 概率判定：proactive_probability（默认 0.6）
  │
  ▼ ⑦ 话题选取：9 类内置话题 + 自定义话题 + Fetcher 资讯注入
  │     （话题去重 + 开场白去重，避免模板感）
  │
  ▼ ⑧ 调用 LLM 生成发言 → 与被动回复共享上下文/记忆/输出管道
  │
  ▼ ⑨ 记录状态：冷却时间、每日计数、话题指纹 → 持久化
```

**话题体系：**

- **9 类内置话题**：分享想法 / 提问讨论 / 回忆过去 / 关注某人 / 活跃气氛 / 科技资讯 / 游戏八卦 / 沙雕新闻 / 热点事件
- **自定义话题**：`proactive_custom_topics` 中按 `|` 分隔添加，与内置话题混合随机选取
- **资讯注入**：资讯类话题（科技/游戏/沙雕/热点）由 Fetcher 模块提供实时素材（RSS 内置 15 个中文源 + 资讯 API），跨群去重，不会多个群发同一条新闻
- **反重复**：6 组开场白模式池随机注入 + 话题指纹去重 + 开场白去重，主动发言不会出现模板感

**效果度量：**

主动发言不是"发完就算"——插件跟踪每群最近 20 条主动发言的 CPS（Contextual Pertinence Score，语境贴合度评分）和采纳率（发言后群内是否有人接话），随时可用 `/wakeup_proactive_metrics` 查看。

### 4.16 五路退却机制

主动发言的前提是"知趣"。五路退却机制确保 Bot 在不受欢迎时立即收声，任一路触发即进入退却状态，退却期内不主动发言：

| 退却路 | 触发条件 | 默认退却时长 | 配置项 |
|--------|---------|-------------|--------|
| 活跃激增 | 群内突然热闹起来，Bot 主动让位 | 1 小时 | `proactive_retreat_active_surge_secs` |
| 连续 SKIP | 主动发言连续被回复抑制拦截 | 1 小时 | `proactive_retreat_consecutive_skip_secs` |
| 连续无回应 | 主动发言后无人接话，按 2h → 6h → 24h 阶梯递增 | 1h 起步，最长 24h | `proactive_retreat_no_response_base_secs` / `proactive_retreat_no_response_max_secs` |
| 厌烦关键词 | 检测到"闭嘴""烦"等针对 Bot 的厌烦信号 | 24 小时 | `proactive_retreat_annoyed_secs` |
| 自说自话 | 检测窗口内 Bot 发言占比超过阈值（默认 2 小时内 80%） | 触发后进入退却 | `proactive_self_talk_ratio` / `proactive_self_talk_hours` |

退却状态可通过 `/wakeup_proactive_status` 实时查看。

### 4.17 回复抑制与轻量回应

**双重回复抑制：**

```
LLM 生成回复
  │
  ▼ 第一层：[SKIP] 关键词前缀拦截（keyword 模式）
  │     回复以 [SKIP] 开头 → 整条拦截，零额外 API 成本
  │     （前缀匹配在发送前执行，思考内容不会泄露到群聊）
  │
  ▼ 第二层：独立小模型合规判别（judge 模式）
  │     由独立小模型判断"这条回复发出去合适吗"
  │     不合适 → 拦截
  │
  ▼ 发送到群聊
```

**轻量回应：** 回复被抑制时，Bot 并非完全消失——按 `light_response_prob`（默认 0.3）的概率掉落一句"确实""有道理"之类的短语，保持存在感而不刷屏。受冷却时间（默认 300 秒）和每小时上限（默认 3 条）约束。

### 4.18 静默时段与状态持久化

**静默时段：** `proactive_quiet_hours` 支持多个时段，支持跨午夜（如 `23:00-07:00,13:00-14:00`）。静默时段内不主动发言。通过单群参数覆盖（`proactive_quiet_hours` 是 21 个可覆盖字段之一），海外时区的群可以单独设置静默时段。发言时间窗（`proactive_time_window_start/end`）与静默时段叠加生效。

**状态持久化：** 主动发言的运行状态（退却状态、冷却时间、每日计数、UMO 映射）持久化到 `data/plugin_data/astrbot_plugin_smart_wakeup/proactive_state.json`（v2.0.1 起；旧位置 `data/proactive_state.json` 的文件会被自动读取迁移），插件重载或 AstrBot 重启后自动恢复，不会出现"重载后 Bot 忘记自己正在退却"的问题。

## 七、回复流程详解

```
用户消息到达
  │
  ▼ ① 记录到消息缓冲区（所有消息，不论是否触发）
  │
  ▼ ② 检查是否需要定期清理
  │
  ▼ ③ 群白名单/黑名单过滤 → 不允许则跳过
  │
  ▼ ④ 指令前缀跳过检查 → 匹配则跳过唤醒判定
  │
  ▼ ⑤ 纯媒体消息检查 → 忽略则跳过
  │
  ▼ ⑥ 更新心流状态（根据消息密度和互动频率）
  │
  ▼ ⑦ 检测触发类型
  │     ├─ 命中名称 → 确定性触发
  │     ├─ 命中关键词 → 按概率触发
  │     ├─ 回复 Bot 消息 → 确定性触发
  │     └─ 未命中 → 概率唤醒判定
  │           ├─ 复读检测 → 复读消息概率乘以 repeat_suppress_factor
  │           ├─ P = base_prob × energy_factor × flow_factor × timing_factor
  │           ├─ 概率命中 → 触发
  │           └─ 未命中 → 仅记录消息，流程结束
  │
  ▼ ⑧ 消息防抖
  │     ├─ force_debounce=关闭 + 名称/回复Bot → 可跳过防抖
  │     ├─ 名称触发 → 等待 debounce_wait_name 秒
  │     ├─ 概率唤醒 → 等待 debounce_wait_prob 秒
  │     └─ 冷场救场 → 等待 debounce_wait_rescue 秒
  │     等待期间有新消息 → 重置定时器（名称触发+force_debounce时不重置）
  │     定时器到期 → 聚合等待期间所有消息
  │
  ▼ ⑨ 消耗精力（energy_decay_rate）
  │
  ▼ ⑩ AstrBot 核心管道接管
  │     ├─ 加载预设人格 & system prompt
  │     ├─ bypass_core_context → 清空核心对话历史
  │     ├─ 注入分层对话记忆（近期原文 + 历史摘要）
  │     ├─ 注入群聊上下文（增量注入 + 摘要压缩）
  │     ├─ 模型路由判定 → 简单消息走小模型，复杂消息走大模型
  │     └─ 调用 LLM 生成回复
  │
  ▼ ⑪ 思考标签过滤（兜底机制）
  │     └─ 正则移除 <think>...</think> 等思考标签
  │
  ▼ ⑫ 消息分段（启用时）
  │     ├─ 智能分段（代码块/引号/缩写保护）
  │     ├─ 均分模式 / 正常模式
  │     ├─ 末尾标点剔除
  │     └─ 按延迟策略分段发送
  │
  ▼ ⑬ 发送回复
  │
  ▼ ⑭ 记录到对话历史 & 缓冲区
  │     ├─ 对话记忆：记录用户消息和 Bot 回复
  │     ├─ 超过 recent_rounds_keep → 触发摘要压缩
  │     └─ 缓冲区：Bot 回复也记录
  │
  ▼ ⑮ 冷场救场检查（定时任务）
        ├─ 群聊停滞超时 → 主动参与对话
        └─ 冷却期内 → 跳过
```

> 上述为**被动回路**（消息触发）。**主动回路**（定时器触发）独立运行：按 `proactive_check_interval` 周期性执行"退却检查 → 静默时段检查 → 条件检查 → 氛围感知 → 概率判定 → 话题选取 → 生成发言"，完整流程见 [4.15 主动发言引擎](#415-主动发言引擎)。两个回路共享同一套上下文工程（分层记忆/关系标注/图片理解/小模型压缩）与输出管道（分段/去重/思考标签过滤/SKIP 拦截）。

## 八、常见问题

### Q: 为什么机器人没有回复？

排查步骤：
1. `/wakeup_status` 检查插件是否正常运行
2. `/wakeup_groups` 检查当前群是否被允许
3. 检查消息是否包含配置的机器人名称或关键词
4. 检查 AstrBot 日志是否有错误信息
5. 确认已配置 LLM 服务商

### Q: 如何获取群聊 ID？

启用插件后，在群中发送消息，查看 AstrBot 日志中 `灵犀` 相关输出，会显示群 ID。Telegram 群 ID 通常为负数，QQ 群 ID 为正数。

### Q: 缓冲区数据会占用多少内存？

每条消息约 100-200 字节，10 条消息约 1-2 KB。200 条消息约 20-40 KB。对内存影响极小。

### Q: 插件重载后数据会丢失吗？

分两类：**唤醒节律数据**（消息缓冲区、对话历史、精力/心流状态等）存储在内存中，插件重载/重启后会清空——这是设计意图，缓冲区仅用于提供近期上下文，不需要持久化；**主动发言状态**（退却状态、冷却时间、每日计数）自 v2.0 起持久化到 `proactive_state.json`（v2.0.1 起位于 `data/plugin_data/astrbot_plugin_smart_wakeup/`，旧位置文件自动迁移），重载后自动恢复，不会丢失。

### Q: 概率唤醒的概率是怎么计算的？

概率唤醒使用动态概率公式：`P = base_prob × energy_factor × flow_factor × timing_factor`。其中：
- `base_prob` 由当前心流状态决定（旁观 0.08、关注 0.20、心流 0.40）
- `energy_factor` 等于当前精力值（0.0 ~ 1.0）
- `flow_factor` 由心流状态映射（旁观/疲劳 0.2、关注 0.8、心流 1.5）
- `timing_factor` 考虑消息间隔等时间因素（0.5 ~ 1.2）

复读消息的概率还会乘以 `repeat_suppress_factor`（默认 0.1）。

### Q: 为什么机器人突然不回复了？

可能原因：
1. **精力耗尽**：精力降至 0 时概率唤醒关闭，使用 `/wakeup_energy` 检查
2. **心流状态降级**：长时间无互动导致退回旁观状态，回复概率大幅降低
3. **冷却期**：冷场救场后进入冷却期
4. **群聊被过滤**：检查 `/wakeup_groups` 确认群未被加入黑名单
5. **复读抑制**：群友正在复读时概率大幅降低，避免打断复读氛围

注意：即使精力为 0，命中名称或关键词时机器人仍会回复。

### Q: 如何调整机器人的活跃程度？

- **提高活跃度**：增大 `flow_flow_prob`、减小 `energy_decay_rate`、减小 `rescue_idle_threshold`
- **降低活跃度**：减小 `flow_bystander_prob`、增大 `energy_decay_rate`、增大 `rescue_cooldown`
- **关闭概率唤醒**：设置 `probability_wakeup = false`，仅名称/关键词触发时回复
- **关闭冷场救场**：设置 `rescue_enabled = false`

### Q: 如何让 Bot 主动说话？

开启 `proactive_enabled`（默认关闭），然后按需调整检查间隔（`proactive_check_interval`）、触发概率（`proactive_probability`）、话题类别等参数。建议先用 `/wakeup_proactive` 手动触发几次观察效果，再放开自动发言。如需实时资讯素材，同时开启 `fetcher_enabled`。

### Q: 为什么 Bot 深夜不主动说话？

这是静默时段机制在保护你的群。`proactive_quiet_hours` 默认为 `23:00-07:00`，支持配置多个跨午夜时段（如 `23:00-07:00,13:00-14:00`）。此外发言时间窗（`proactive_time_window_start/end`，默认 09:00~23:00）也会限制主动发言时段。海外时区的群可通过单群参数覆盖单独配置。

### Q: 主动发言会不会很烦人？

五路退却机制专门为此设计：群内突然热闹时 Bot 主动让位、主动发言无人接话时按 2h/6h/24h 阶梯退却、检测到厌烦关键词时长时间收声、自说自话占比过高时自动静默。另有每日上限（默认 20 条）和发言冷却（默认 30 分钟）兜底。可用 `/wakeup_proactive_status` 随时查看退却状态，用 `/wakeup_proactive_metrics` 查看发言采纳率。

### Q: 如何更换或新增 RSS 资讯源？

开启 `fetcher_enabled` 后，在 `fetcher_rss_feeds` 中添加自定义源，支持三种格式：`类别|URL1,URL2;类别2|URL3`、`类别:URL`、每行一个 URL；留空时使用内置的 15 个中文资讯源（科技/游戏/沙雕/热点 4 大类），开箱即用。

### Q: 如何为特定群设置不同的参数？

在「高级设置 → 单群参数覆盖」中添加群组覆盖项，填写群 ID 和需要覆盖的字段即可。未填写的字段使用全局默认值。

### Q: 上下文压缩和对话记忆有什么区别？

- **上下文压缩**：压缩的是注入给 LLM 的群聊消息上下文（其他人的发言），减少 token 消耗
- **对话记忆**：保留的是 Bot 与用户之间的多轮对话历史（用户消息 + Bot 回复），确保多轮对话连贯

两者互补，建议同时开启。

### Q: 模型路由怎么用？

1. 配置一个小模型提供商 ID 到 `routing_small_model`（如 `Volcengine/doubao-seed-2-0-lite-260215`）
2. 开启 `model_routing_enabled`，简单消息将走小模型，复杂消息仍由大模型处理

注意：`cascade_upgrade_enabled`（级联升级）当前版本未实现，保留仅为兼容旧配置，开启后无任何效果。

### Q: 思考标签过滤什么时候需要开启？

推荐保持默认开启。使用推理类模型（如 DeepSeek-R1、QwQ、GLM 等）时，模型可能在回复中输出 `<think>` 标签，此过滤器作为兜底机制确保思考内容不会泄露到群聊。

### Q: 消息分段适合什么场景？

消息分段适合 Bot 经常生成较长回复的场景。启用后长回复会被智能分段发送，配合延迟策略模拟真人输入节奏，避免一大段文字突然出现。如果 Bot 回复通常较短，可以不启用。

### Q: QQ 平台有什么特殊注意事项？

QQ 通过 aiocqhttp 适配器接入，群 ID 为正数。其他功能与 Telegram 一致，无特殊差异。确保 AstrBot 已正确配置 aiocqhttp 适配器。

### Q: 图片上下文关联应该选哪种模式？

- **框架图片描述**：适合已配置 `group_chat_context` 插件且希望零额外成本的用户，无需任何开关，但描述可能延迟到达
- **自定义模型识别（降级方案）**：适合框架图片描述功能异常、需要备用识别通道的用户，需配置支持图片输入的多模态模型，每张图片额外消耗一次 API 调用

两种来源为主备降级关系：优先使用框架图片描述，框架未提供时才走自定义模型。

### Q: 在场用户感知和对话关系标注可以关闭吗？

这两个功能始终启用，无需配置。它们通过在上下文中添加结构化标注和系统提示来增强 LLM 的理解能力，不增加额外的 API 调用成本。
