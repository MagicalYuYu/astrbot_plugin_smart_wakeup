# 灵犀 - 故障处理与调试指南

> 遇到问题时不要慌，按本文档的流程一步步排查，大部分情况都能自行解决。

---

## 一、故障处理总览

```
发现问题
  │
  ▼ 第一步：开启调试模式
  │
  ├─ 小型故障（回复异常、参数不适配、行为不符合预期等）
  │   └─ 导出后台日志 → 交给 AI 辅助排查 → 自行解决
  │
  └─ 严重故障（插件崩溃、功能完全失效、报错无法恢复等）
      └─ 导出后台日志 → 交给 AI 辅助排查
          │
          ├─ 判定为非插件问题（AstrBot/平台/模型等）→ 按指引处理
          └─ 判定为插件问题 → 汇总故障信息 → 向作者报备
```

**核心原则**：先开调试、再看日志、AI 先查、再报作者。

## 二、调试模式

### 2.1 如何开启

AstrBot WebUI → 插件管理 → 灵犀 → 配置 → 基础设置 → **调试模式** → 开启

> 开启后会在 AstrBot 后台日志中输出详细的判定过程信息。正常使用时建议关闭以减少日志量。

### 2.2 调试日志包含什么

开启调试模式后，每条群消息都会在日志中输出：

| 信息 | 说明 |
|:-----|:-----|
| 触发类型 | 名称命中 / 关键词命中 / 概率唤醒 / 冷场救场 / 复读抑制 |
| 概率计算 | base_prob × energy_factor × flow_factor × timing_factor 的具体数值 |
| 心流状态 | 当前状态（旁观/关注/心流/疲劳）及转换原因 |
| 精力值 | 当前精力百分比 |
| 防抖状态 | 等待时间、暂存消息数 |
| 分段信息 | 分段数量、每段内容摘要 |

### 2.3 调试日志位置

AstrBot 后台日志。查看方式：
- **Docker 部署**：`docker logs <容器名>`
- **直接运行**：AstrBot 控制台输出或日志文件
- **WebUI**：部分 AstrBot 版本支持在 WebUI 中查看日志

### 2.4 快速状态检查

无需开启调试模式，在群聊中发送调试指令即可：

| 指令 | 作用 |
|:-----|:-----|
| `/wakeup_status` | 插件运行状态、统计、缓冲区概览 |
| `/wakeup_energy` | 当前群精力状态 |
| `/wakeup_flow` | 当前群心流状态 |
| `/wakeup_token` | Token 消耗统计 |
| `/wakeup_buffer` | 消息缓冲区内容 |

## 三、日志导出与 AI 辅助排查

### 3.1 如何导出日志

1. 开启调试模式后，让 Bot 运行一段时间（至少触发一次你关注的问题）
2. 从 AstrBot 后台复制相关日志段落
3. 建议只截取问题发生前后 5-10 分钟的日志，避免信息过多

> **脱敏提醒**：日志中可能包含群 ID、用户名等信息。如果需要分享给他人，请先替换或删除敏感数据。

### 3.2 AI 辅助排查提示词

将日志交给 AI（如 ChatGPT、Claude、GLM 等）时，使用以下提示词模板可获得更准确的分析：

#### 小型故障提示词模板

```
我正在使用一个 AstrBot 平台的聊天插件「灵犀」（astrbot_plugin_smart_wakeup），遇到了以下问题：

【问题描述】
（在这里描述你遇到的问题，例如：Bot 在群里回复太频繁 / Bot 不回复 / 分段异常等）

【运行环境】
- AstrBot 版本：（如 v4.5.0）
- 平台：Telegram / QQ (aiocqhttp)
- 插件版本：1.0.0

【调试日志】
（在这里粘贴从后台复制的日志）

请分析日志，找出问题原因，并给出具体的解决建议（包括需要调整的配置参数和推荐值）。
```

#### 严重故障提示词模板

```
我正在使用一个 AstrBot 平台的聊天插件「灵犀」（astrbot_plugin_smart_wakeup），遇到了严重故障：

【故障现象】
（描述故障，例如：插件崩溃 / 功能完全失效 / 持续报错等）

【错误信息】
（粘贴报错信息，如果有的话）

【调试日志】
（粘贴后台日志）

【运行环境】
- AstrBot 版本：
- 平台：Telegram / QQ (aiocqhttp)
- Python 版本：
- 插件版本：1.0.0

请分析：
1. 这个故障是否由插件本身引起？
2. 如果是插件问题，请帮我汇总一份故障报告，方便我向插件作者报备。
3. 如果不是插件问题，请指出可能的原因和解决方向。
```

### 3.3 如何判断故障是否源于插件

AI 分析结果中，关注以下信号：

| 信号 | 含义 |
|:-----|:-----|
| 日志中出现 `灵犀` 相关的 `Error` 或 `Traceback` | 大概率是插件问题 |
| 日志中插件流程正常但 LLM 返回异常 | 可能是模型/网络问题，非插件问题 |
| 日志中完全没有 `灵犀` 相关输出 | 插件可能未正确加载，或消息被过滤 |
| 日志显示概率计算正常但未触发回复 | 参数设置问题，非 bug |
| `CancelledError` 且来源为其他插件 | 非本插件问题 |

## 四、作者报备规范

### 4.1 何时需要报备

- 确认是插件的 bug（功能异常、崩溃、报错等）
- 按本文档流程排查后仍无法自行解决
- 发现了文档未覆盖的边界情况

**不需要报备的情况**：
- 参数不适配（请参考第五章自行调优）
- 模型返回质量不佳（非插件问题）
- 其他插件的报错（请联系对应插件作者）

### 4.2 报备信息模板

请前往 GitHub Issues 提交，按以下格式填写：

```markdown

（描述实际发生的异常行为）

（粘贴脱敏后的日志，或上传日志文件）

## 运行环境
- AstrBot 版本：
- 平台：Telegram / QQ (aiocqhttp)
- Python 版本：
- 插件版本：1.0.0

## 补充信息
（其他有助于排查的信息）
```

## 五、QA 参数调试指南

### 5.1 回复频率偏高

**场景**：Bot 在群里说话太多，感觉不像真人

按以下优先级逐步调整，每次调一项，观察 1-2 天：

| 优先级 | 调整参数 | 默认值 | 建议调整 | 说明 |
|:------:|:---------|:------:|:--------:|:-----|
| 1 | `flow_flow_prob` | 0.40 | 0.25 | 心流状态回复概率，影响最大 |
| 2 | `flow_attentive_prob` | 0.20 | 0.12 | 关注状态回复概率 |
| 3 | `energy_decay_rate` | 0.15 | 0.25 | 精力消耗速率，越大越容易累 |
| 4 | `energy_recovery_rate` | 0.02 | 0.01 | 精力恢复速率，越小恢复越慢 |
| 5 | `repeat_suppress_factor` | 0.1 | 0.05 | 复读抑制系数，越小抑制越强 |

**极端方案**：如果以上调整仍不满意，直接关闭概率唤醒——设置 `probability_wakeup = false`，Bot 将只在被叫到名字或命中关键词时才回复。

### 5.2 回复频率偏低

**场景**：Bot 太沉默，很少主动参与对话

按以下优先级逐步调整：

| 优先级 | 调整参数 | 默认值 | 建议调整 | 说明 |
|:------:|:---------|:------:|:--------:|:-----|
| 1 | `flow_bystander_prob` | 0.08 | 0.15 | 旁观状态回复概率，提升沉默时的主动性 |
| 2 | `flow_attentive_prob` | 0.20 | 0.30 | 关注状态回复概率 |
| 3 | `energy_decay_rate` | 0.15 | 0.08 | 精力消耗速率，越小越不容易累 |
| 4 | `energy_recovery_rate` | 0.02 | 0.04 | 精力恢复速率，越大恢复越快 |
| 5 | `rescue_idle_threshold` | 300 | 180 | 冷场判定时间（秒），越小越早救场 |
| 6 | `rescue_cooldown` | 1800 | 900 | 救场冷却时间（秒），越小救场越频繁 |

### 5.3 参数调优实操方法

推荐**单变量法**——最科学、最可控的调优方式：

1. **每次只调一个参数**，记录调整前的值和新值
2. **观察 1-2 天**，让系统在不同对话场景下充分运行
3. **使用调试指令监控**：
   - `/wakeup_energy` — 查看精力消耗和恢复是否合理
   - `/wakeup_flow` — 查看心流状态转换是否自然
   - `/wakeup_status` — 查看整体回复统计
4. **必要时开启 debug_mode**，观察概率计算的具体数值
5. **调优满意后关闭 debug_mode**，减少日志量

> 调优没有"标准答案"，取决于你的群聊氛围和期望的 Bot 人设。建议从默认值开始微调，而非大幅改动。

### 5.4 常见调优场景速查表

| 场景 | 调整参数 | 方向 | 所在配置组 |
|:-----|:---------|:----:|:-----------|
| Bot 太爱搭话 | `flow_flow_prob` | ↓ | 心流状态机 |
| Bot 从不主动说话 | `flow_bystander_prob` | ↑ | 心流状态机 |
| Bot 回复后很快又回复 | `energy_decay_rate` | ↑ | 精力系统 |
| Bot 回复一次就消失了 | `energy_decay_rate` | ↓ | 精力系统 |
| Bot 精力恢复太慢 | `energy_recovery_rate` | ↑ | 精力系统 |
| 群里复读时 Bot 频繁触发回复 | `repeat_suppress_factor` | ↓ | 基础设置 |
| 冷场了 Bot 也不救场 | `rescue_idle_threshold` | ↓ | 冷场救场 |
| Bot 救场太频繁 | `rescue_cooldown` | ↑ | 冷场救场 |
| Bot 总是打断别人说话 | `debounce_wait_prob` | ↑ | 消息防抖 |
| 关键词触发概率太高 | `keyword_reply_prob` | ↓ | 基础设置 |
| Token 消耗太大 | 开启 `context_compression_enabled` | — | 基础设置 |
| 长回复一大段不好看 | 开启 `splitter.enabled` | — | 消息分段 |

## 六、常见问题

### Q: 插件支持哪些平台？

Telegram 和 QQ（通过 aiocqhttp 适配器接入）。两个平台功能一致，群 ID 格式不同：Telegram 群 ID 通常为负数，QQ 群 ID 为正数。

### Q: 插件数据会持久化吗？

不会。所有运行时数据（消息缓冲区、精力/心流状态、对话历史等）存储在内存中，AstrBot 重启或插件重载后清空。这是设计意图——缓冲区仅用于提供近期上下文，无需持久化。

### Q: 多个群可以独立配置吗？

可以。在「高级设置 → 单群参数覆盖」中为特定群设置独立参数，未覆盖的字段使用全局默认值。

### Q: 如何完全关闭概率唤醒，只保留名称触发？

设置 `probability_wakeup = false`。此时 Bot 只在消息包含名称或关键词时才回复，不会主动参与对话。

### Q: Token 消耗太大怎么办？

1. 开启 `context_compression_enabled`（上下文压缩），用小模型压缩群聊上下文
2. 开启 `bypass_core_context`（绕过核心上下文），避免重复注入
3. 减小 `context_messages_count`（上下文消息数量）
4. 开启 `incremental_context_enabled`（增量注入），避免重复内容
5. 如有条件，配置独立的小模型用于压缩（`compression_model`）

### Q: 如何选择压缩模型？

推荐选择轻量、低延迟、低成本的模型，如：
- 火山引擎 Doubao Seed Lite
- DeepSeek V3
- 其他低成本 API

关键是模型能理解中文对话内容并生成准确的摘要，不需要很强的推理能力。

### Q: 分段后标点被去掉了怎么办？

分段模块默认剔除末尾的语气中性标点（句号、分号、冒号等），这是为了让回复更符合自然聊天习惯。如果不希望剔除：
1. 关闭 `strip_trailing_punct_enabled`
2. 或修改 `strip_trailing_punct_chars`，移除不想剔除的字符

### Q: 如何让 Bot 只在特定群生效？

在「群组过滤」中启用白名单，将目标群 ID 加入 `enabled_groups` 列表。未在白名单中的群不会触发任何唤醒。

### Q: 插件和 AstrBot 原生 @ 机制冲突吗？

不冲突。插件处理的是"自然唤醒"（名称/关键词/概率），AstrBot 原生的 @ 触发走独立通道。两者可以同时使用。

### Q: 如何卸载插件？

在 AstrBot WebUI → 插件管理中禁用或卸载灵犀插件。卸载后所有运行时数据自动清理，无需手动操作。

### Q: 为什么机器人没有回复？

排查步骤：
1. `/wakeup_status` 检查插件是否正常运行
2. `/wakeup_groups` 检查当前群是否被允许
3. 检查消息是否包含配置的机器人名称或关键词
4. 检查精力是否耗尽（`/wakeup_energy`）
5. 检查 AstrBot 日志是否有错误信息
6. 确认已配置 LLM 服务商

### Q: 为什么机器人突然不回复了？

可能原因：
1. **精力耗尽**：精力降至 0 时概率唤醒关闭，使用 `/wakeup_energy` 检查
2. **心流状态降级**：长时间无互动导致退回旁观状态，回复概率大幅降低
3. **冷却期**：冷场救场后进入冷却期
4. **复读抑制**：群友正在复读时概率大幅降低，避免打断复读氛围

注意：即使精力为 0，命中名称或关键词时机器人仍会回复。

### Q: 概率唤醒的概率是怎么计算的？

动态概率公式：`P = base_prob × energy_factor × flow_factor × timing_factor`

- `base_prob` 由心流状态决定（旁观 0.08、关注 0.20、心流 0.40）
- `energy_factor` 等于当前精力值（0.0 ~ 1.0）
- `flow_factor` 由心流状态映射（旁观/疲劳 0.2、关注 0.8、心流 1.5）
- `timing_factor` 考虑消息间隔等时间因素（0.5 ~ 1.2）

复读消息的概率还会乘以 `repeat_suppress_factor`（默认 0.1）。

### Q: 开启图片识别后 Bot 回复变慢了？

`image_context_wait_max` 设置过大时，防抖等待时间会被延长以等待图片描述生成。将 `image_context_wait_max` 设为 `0`（默认值）可避免额外等待，Bot 会按正常防抖时间回复，图片描述会在后台异步生成并注入下次上下文。

### Q: 自定义模型图片识别报错"未找到提供商"？

检查 `image_context_custom_model_id` 填写的是完整的提供商 ID（如 `Volcengine/doubao-vision-pro-32k`），而非模型名称。提供商 ID 需与 AstrBot 中配置的 LLM 提供商 ID 完全一致，可在 AstrBot WebUI → 服务提供商中查看。

### Q: Bot 仍然对不在场的用户说话？

在场用户感知是提示词层面的约束，通过 `<presence_awareness>` 系统提示引导 LLM 只对近期活跃用户说话。如果人格提示词中包含冲突指令（如"对所有用户友好回应"），可能削弱此约束效果。建议在人格提示词中配合强调"只对在场用户说话"。

### Q: 两种图片识别模式可以同时开启吗？

两种模式互斥，同时开启时插件会自动关闭系统图片识别模式，以自定义模型模式为准。日志中会出现警告：`[ImageContext] 系统图片识别和自定义模型图片识别同时开启，优先使用自定义模型模式，关闭系统模式`。建议只开启需要的一种模式。
